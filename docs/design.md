# WiFi AP 配置計画ツール 設計

本書は `requirements.md` の要件を実装するための設計を定める。
要件の番号（FR-x.x、NFR-x）は要件ファイルのものを指す。

## 1. 全体構成

システムは、ブラウザで動く Web アプリと、API と同期を担うサーバの二つで構成する。
データベースは SQLite から始め、サーバと同じコンテナのボリュームにファイルとして置く（2.5 節）。
伝搬計算はブラウザの Web Worker で行い、壁の自動抽出と PDF のラスタ化はサーバの worker thread で行う。

```
┌──────────── ブラウザ ────────────┐        ┌──────────── app コンテナ ────────────┐
│ React UI（2D エディタ / 3D ビュー）│  HTTP  │ Hono（@hono/node-server）             │
│   │                               │◀──────▶│  ├ REST API（認証、プロジェクト、     │
│   ├ Y.Doc ◀─ HocuspocusProvider ──┼── WS ──┼─▶│   ファイル、AP モデル、壁抽出）   │
│   │    └ y-indexeddb（オフライン） │        │  ├ Hocuspocus（Yjs 同期）            │
│   └ 伝搬計算 Worker               │        │  └ worker thread プール              │
└───────────────────────────────────┘        │      （PDF ラスタ化、壁抽出）         │
                                              └──────┬───────────────┬──────────────┘
                                                     │               │
                                                  SQLite       アップロード領域
                                               （ボリューム）   （ボリューム）
```

```

  Dockerfile

```

`propagation` と `wall-extraction` を独立したパッケージにするのは、UI とサーバを起動せずに単体テストとベンチマークを回すためである。
`propagation` は将来の実測サーベイとの比較（7 章）でも、任意の地点の推定値を求めるために使う。

## 2. データの置き場所

データは、共同編集の対象になるものを Yjs 文書に、それ以外をデータベースに置く。
境界は次のとおりとする。

- **Yjs 文書（プロジェクトごとに一つ）**：プロジェクト設定、材質、フロア、図面の変換情報、壁、AP、現場写真のピン、プロジェクト内に取り込んだ AP モデルの写し。
- **データベース**：ユーザー、セッション、プロジェクトの一覧と権限、AP モデルのライブラリ、ファイルのメタデータ、Yjs 文書の保存先。
- **アップロード領域**：図面の元ファイル、ラスタ化した図面画像、写真と縮小画像。SHA-256 をファイル名にした内容アドレス方式で置く。

### 2.1 データベースのテーブル

| テーブル | 主な列 | 備考 |
| --- | --- | --- |
| users | id, username, password_hash, is_admin, disabled_at | パスワードは argon2id |
| sessions | id, user_id, expires_at | Cookie のセッション ID を引く |
| projects | id, name, owner_id, created_at, updated_at, deleted_at | |
| project_members | project_id, user_id, role（viewer / editor） | 所有者は projects.owner_id で表す |
| yjs_documents | project_id, state（blob）, updated_at | Hocuspocus の Database 拡張が読み書きする |
| blobs | sha256, mime, size, created_at | 実体はアップロード領域 |
| project_files | project_id, sha256, kind（plan_source / plan_image / photo / thumbnail）, original_name | プロジェクトとファイルの対応。権限確認に使う |
| ap_models | id, name, vendor, definition（JSON 文字列）, created_by, updated_at | 全ユーザー共有のライブラリ（FR-5.4） |
| survey_datasets | id, project_id, floor_id, … | 将来対応のため予約（7 章）。今回は作成しない |

### 2.2 Yjs 文書の構造

文書のルートに次の `Y.Map` を置く。
各要素は ID をキーにした `Y.Map` とし、要素のフィールドごとに最後の書き込みが勝つ形で収束させる。
壁の頂点列のように一体で意味を持つ値は、フィールド全体を置き換える。

```ts
root = {
  meta:      { schemaVersion: number },
  settings:  {
    receiverHeightM: 1.0,            // FR-7.3
    gridResolutionM: 0.5,            // FR-7.3
    pathLossExponent: { "2.4": 2.0, "5": 2.0, "6": 2.0 },  // FR-7.4
    rxGainDbi: 0,
    legend: { thresholds: [...], goodThresholdDbm: -67, hideBelow: boolean }, // FR-8.4
    crossFloorRange: number | null,  // FR-7.8。null は全フロア、0 は同じフロアだけ、n は上下 n フロアまで。版 3 で追加
  },
  materials: Map<materialId, { name, color, lossDb: { "2.4", "5", "6" }, presetKey? }>,
  apModels:  Map<modelId, ApModelSnapshot>,  // 2.3 節
  floors:    Map<floorId, {
    name, order, elevationM, heightM,
    plan: { sourceSha256, page?, dpi?, imageSha256, unitsPerPx, rotationDeg, crop? },
    scale?: { a: Vec2, b: Vec2, distanceM: number },   // FR-2.4。未設定なら未校正
    alignment?: { a: Vec2, b: Vec2 },                   // FR-3.2 の基準点（図面座標）
    walls:  Map<wallId, Wall>,
    aps:    Map<apId, Ap>,
    photoPins: Map<pinId, PhotoPin>,
    holes:  Map<holeId, { points: Vec2[] }>,          // FR-3.8 の吹き抜け（図面座標の閉じた多角形）。版 2 で追加
    slabMaterialId?: string,                          // FR-3.1、FR-7.6 の床スラブの材質。版 3 で追加
  }>,
}
```

文書の形は `packages/domain` の zod スキーマで定義し、読み込み時に検証する。
`meta.schemaVersion` を上げるときは、サーバが文書を開く時点でマイグレーションを適用する。

版 3 のマイグレーションでは、材質に床スラブのプリセット（4.2 節）が無ければ足し、各フロアの `slabMaterialId` をそれにし、`crossFloorRange` を `null`（全フロア）にする。
マイグレーションの前の文書がブラウザに残っていると、統合したときに足す前の値が勝つことがある（版 2 の `holes` と同じ）。
そのため、`crossFloorRange` が無ければ `null` とみなし、`slabMaterialId` が無いか指す材質が無ければ、`presetKey` が `"slab"` の材質を使う。それも無ければ床スラブの減衰を 0 dB とし、画面で知らせる。

### 2.3 AP モデルのライブラリと写し

AP を配置するとき、ライブラリの AP モデルの定義を文書の `apModels` に写し、AP はその写しを参照する。
写しには元のモデルの ID と更新日時を残し、ライブラリ側が新しくなったら UI で更新を提案する。

ライブラリを直接参照する方式を採らないのは、他のユーザーがライブラリのモデルを編集、削除したときに、既存プロジェクトの計算結果が知らないうちに変わるためである。
写しを持つことで、エクスポートしたファイルもライブラリなしで完結する。

### 2.4 複製、エクスポート、インポート、バックアップ

- **複製（FR-1.3）**：新しいプロジェクト行を作り、Yjs 文書の状態をそのまま写し、`project_files` の行を複製する。ファイルの実体は内容アドレスなので写さない。
- **削除（FR-1.3）**：`deleted_at` を立てて一覧から外す。どのプロジェクトからも参照されなくなった blob は、定期処理で削除する。
- **エクスポート（FR-1.5）**：ZIP に `manifest.json`（形式のバージョン）、`project.json`（Yjs 文書を普通の JSON に変換したもの）、`files/<sha256>` を入れる。
- **インポート（FR-1.5）**：`project.json` を zod で検証し、マイグレーションを適用してから新しい Y.Doc を組み立てる。ID はプロジェクト内で閉じているので付け替えない。
- **バックアップ（NFR-6）**：SQLite の `VACUUM INTO` でデータベースの写しを作り、アップロード領域とあわせて tar にまとめるスクリプトを用意する。復元手順も同じ場所に書く。

エクスポートに Yjs のバイナリではなく JSON を使うのは、編集履歴を持ち出さずに済み、スキーマのマイグレーションを通常の JSON 変換として書けるためである。

バックアップでデータベースのファイルをそのまま複製しないのは、書き込み中に複製すると壊れた写しになることがあるためである。
`VACUUM INTO` はサーバを止めずに一貫した写しを作れる。

### 2.5 SQLite から始めることの前提

サーバは単一のプロセスで動かし、SQLite には WAL モードで接続する。
想定する規模（NFR-3 の同時編集者 3〜5 人）では、書き込みの大半は Hocuspocus がデバウンスをかけて行う文書の保存なので、単一プロセスの SQLite で足りる。

後で PostgreSQL に移せるように、次の制約を守る。

- テーブル定義とクエリは Drizzle を通して書き、SQL を直接書かない。
- JSON は文字列の列に入れ、データベースの JSON 関数で中を検索しない。
- 日時は UTC の ISO 8601 文字列か UNIX 時刻の整数で持つ。
- データベースへのアクセスはリポジトリ層に閉じ込め、Drizzle のスキーマを方言ごとに差し替えられるようにする。

サーバを複数のプロセスに増やす必要が出たら、PostgreSQL に移し、Hocuspocus の Redis 拡張でプロセス間の同期を行う。

## 3. 座標系

座標系を三つ定める。

- **図面座標**：図面の元ページ上の位置。単位は PDF ならポイント（1/72 インチ）、画像ならピクセルとする。壁、AP、写真ピンの位置はすべてこの座標で保存する。
- **フロア座標**：図面座標を、図面の回転（`rotationDeg`）で回し、スケールでメートルに換算し、y 軸を上向きに反転したもの。高さ方向（z）を上に取ったときに右手系になるよう、y を反転する。伝搬計算はフロア座標で行う。AP の方位角はフロア座標の +x 軸から反時計回りに測る。
- **ワールド座標**：プロジェクトで共通の座標。基準フロア（スケールを校正済みのフロアのうち、`order` が最小のフロア）のフロア座標をワールド座標とし（ワールド座標では何も保存しないので、フロアを並べ替えて基準フロアが変わっても保存データは変わらない）、他のフロアは基準点 2 点の対応から求めた回転と平行移動でワールド座標に移す。高さ方向は `elevationM` に床からの高さを足す。

位置を図面座標で保存する理由は、図面に対する操作で要素がずれないようにするためである。
スケールを校正し直すと、フロア座標での長さは変わるが、図面上の位置は変わらない。
トリミング（`crop`）は表示範囲を決めるだけで、座標の原点を動かさない。
PDF を別の解像度でラスタ化し直しても、`unitsPerPx`（画像の 1 ピクセルが何ポイントか）が変わるだけで、保存済みの座標は変わらない。
PDF の図面座標はポイントなので、縮尺 1:N の図面なら 1 単位が N × 0.0254 / 72 m になる。取り込み時に縮尺を入力したときは、ページの上端の 2 点（`(0, 0)` と `(ページ幅, 0)`）と、紙面の幅に縮尺を掛けた実距離を `scale` に書く（保存の形は 2 点を選んだ校正と同じ）。元の用紙サイズ（例：A1 の図面を A3 に縮小した PDF なら A1）を指定したときは、長辺の比で紙面の幅を拡大してから縮尺を掛ける。
取り込んだあとに「スケールを数値で設定」から縮尺か 1 m あたりの図面上の長さを入力したときも、同じくページの上端の 2 点で `scale` を書く。ページの大きさは `widthPx × unitsPerPx` で求める。

フロア間の位置合わせ（FR-3.2）では、各フロアのスケールを固定したまま、回転と平行移動だけを求める。
2 点間の距離がフロアどうしで一定以上食い違うときは、スケール校正の誤りの可能性があるとして警告を出す。

## 4. 壁と材質

### 4.1 壁の表現

```ts
type Wall = {
  points: Vec2[];            // 図面座標の折れ線。2 点以上
  materialId: string;
  bottomM?: number; topM?: number;  // 床からの高さの範囲（FR-4.10）。無ければ 0 と階高。版 3 で追加
  openings: {                // ドア、窓（FR-4.8）
    id: string;
    kind: "door" | "window" | "other";
    start: number; end: number;   // 折れ線に沿った距離（図面座標）
    materialId: string;
    bottomM?: number; topM?: number;  // 床からの高さの範囲。無ければ壁と同じ
  }[];
};
```

開口部を別の壁ではなく壁の区間として持つのは、壁を移動したときに開口部が一緒に動くようにするためである。

壁の高さは、フロアの床面からの高さ（メートル）で持つ。
無いときに階高を使うのは、階高を変えたときに、高さを指定していない壁が一緒に伸び縮みするようにするためである。
`topM` は階高を超えてもよい。吹き抜けに面した、上のフロアまで続く壁を、下のフロアの壁一つで表せる。
`bottomM` は 0 以上、`topM` は `bottomM` より大きくする。

開口部の高さは、壁の高さの範囲で切り取って使う。
開口部の区間のうち、開口部の高さの範囲は開口部の材質、それ以外で壁の高さの範囲に入る部分は壁の材質とする。
たとえば、高さ 0〜2.0 m のドアでは、ドアの上から天井までは壁の材質になる。
開口部の高さは版 1 から型にあったが、UI では書いておらず、計算にも表示にも使っていなかった。

#### 4.1.1 高さの範囲が重なる壁の警告

同じ線の上に重ねて描いた壁は、経路が横切ると両方の減衰を加える（6.1.1 節）。
高さの範囲が重ならなければ（腰壁と、その上の下がり壁など）正しいが、重なればその部分を二重に数える。
これを知らせるため、次のすべてを満たす壁区間の組を「重なる壁」として警告する（FR-4.11）。

- 平面で、向きの差が 1° 以内、互いの直線からの距離が 0.05 m 以内で、線に沿った重なりが 0.1 m 以上ある。
- 絶対の高さの範囲（床面の標高に `bottomM` と `topM` を足したもの）が重なる。範囲は半開区間なので、上端と下端が接するだけなら重ならない。

開口部は壁の範囲の中の区別なので、判定には壁の高さの範囲だけを使う。
対象は、表示中のフロアの壁どうしと、表示中のフロアの壁とワールド座標に置ける他のフロアの壁（位置合わせ済みのもの）の組とする。
壁は多くても数千本なので、外接矩形で絞ってから全組を調べ、メインスレッドで行う。

2D ビューでは、重なる壁区間を警告の色で縁取り、件数を示す。
件数の表示から、表示中のフロアの該当する壁をまとめて選択できる。

分割と結合（FR-4.4）では、開口部を次のように扱う。

- **分割**：分割位置より前の開口部は前の壁に、後ろの開口部は位置をずらして後ろの壁に移す。分割位置をまたぐ開口部は二つに切る。
- **結合**：端点を共有し、材質と高さの範囲が同じ 2 本の壁だけを結合できる。後ろの壁の開口部は、前の壁の長さだけずらす。向きが逆なら頂点列と開口部の位置を反転してから結合する。

### 4.2 材質

材質はプロジェクトの文書に持ち、新規プロジェクトには次のプリセットを入れる。
数値は一般的な文献値に基づく初期値であり、利用者が調整する前提とする。

| 材質 | 2.4 GHz | 5 GHz | 6 GHz |
| --- | --- | --- | --- |
| コンクリート壁 | 12 | 20 | 24 |
| コンクリートブロック | 8 | 12 | 14 |
| 石膏ボード間仕切り | 3 | 4 | 5 |
| ガラス | 2 | 4 | 5 |
| Low-E ガラス | 10 | 20 | 25 |
| 木製ドア | 3 | 4 | 5 |
| 金属扉 | 15 | 20 | 25 |
| RC 床スラブ | 20 | 25 | 28 |

単位は dB である。
プリセットを削除しても、他のプロジェクトには影響しない。

壁と床スラブで材質の表を分けず、どちらにもどの材質でも選べるようにする。
木造の床や鉄骨造のデッキプレートの床など、床にも建物ごとの違いがあり、利用者が材質を足して選べるようにするためである。
新しいフロアの床スラブは、`presetKey` が `"slab"` の材質にする。無ければ未設定とする。

### 4.3 選択と編集

選択状態（FR-4.5）はユーザーごとのローカル状態とし、Yjs 文書には書かない。
選択中の壁をドラッグせずにクリックしたときは、その壁だけを選ぶ（ドラッグしたときは選択中の壁をまとめて動かす）。
壁の描画の確定に使うダブルクリックは、ブラウザが数えるクリックの回数で判定する。
Konva のダブルクリックのイベントは離れた位置の素早い 2 回のクリックでも発生し、描画中の点を取りこぼすためである。
他のユーザーへの表示（FR-10.3）は awareness で行う。
一括の材質変更、高さの範囲の変更、削除（FR-4.6）は一つの Yjs トランザクションで書き、undo で一度に戻せるようにする。
高さの範囲は、既定（0 m と階高）に戻す操作も用意する。選択した壁の値がそろっていなければ、入力欄を空にして「混在」と示す。

### 4.4 スナップ

壁の描画、壁の頂点の移動、スケール校正、位置合わせ、トリミングで置く点はスナップする（FR-4.4）。
優先の順は、既存の壁の端点、図面の線の交点、図面の線の端点、既存の壁の上の点、
直前の点から縦横に引いた線と図面の線の交わり、図面の線の上の点、直前の点からの直交方向とする。
既存の壁を図面の線より優先し、描いた壁どうしのつながりを崩さない。距離は画面で 10 ピクセル以内とし、Alt を押している間はスナップしない。

図面の線は、ユーザーが有効にしたときに、壁の自動抽出のジョブ（9 章）を、輪郭の前処理、Hough 変換、平行な線をまとめない設定で動かして得る。
壁の両側の線にスナップできるよう、平行な線はまとめない。結果はユーザーごとのローカル状態とし、図面の画像かトリミングが変わるまで使い回す。
交点は、向きの差が 15° 以上の線分の組について、角で線が少し手前で止まっていても交わるよう両端を 4 ピクセル延ばして求め、1 ピクセル以内の交点は 1 点にまとめる。
線分が数千本になっても、交点の計算とマウスの移動ごとの検索が速く終わるよう、線分と点を格子のバケツに入れ、近くのものだけを調べる。
A3 を 200 dpi でラスタ化した合成図面の線分を 20 倍に増やした約 2000 本で、交点の計算が 42 ms、1 回の検索が 0.05 ms だった。

## 5. AP とアンテナパターン

### 5.1 AP モデル

```ts
type ApModel = {
  name: string; vendor?: string;
  radios: {
    key: string;                       // "radio0" など
    bands: ("2.4" | "5" | "6")[];      // 対応帯域
    maxTxPowerDbm: Record<Band, number>;
    pattern: AntennaPattern;
  }[];
};

type AntennaPattern =
  | { kind: "omni"; gainDbi: number }
  | { kind: "directional";                               // 5.2 節の指向性パターン
      azimuthCut:   { deg: number; gainDbi: number }[];   // -180〜180
      elevationCut: { deg: number; gainDbi: number }[];   // -90〜90
      perBand?: Partial<Record<Band, { azimuthCut; elevationCut }>>; }
  | { kind: "axial";                                     // 5.2 節の軸対称に近いパターン
      offAxisCut: { deg: number; gainDbi: number }[];     // 軸からの角度 0〜180
      aroundAxisCut: { deg: number; gainDbi: number }[];  // 軸まわりの角度 0〜360
      rollOffsetDeg: number;
      perBand?: Partial<Record<Band, { offAxisCut; aroundAxisCut }>>; };
```

CSV と JSON の取り込み（FR-5.2）はサーバで zod により検証し、取り込んだ点列をそのまま保存する。
1 度刻みの表への補間は、伝搬計算の前にクライアントで行う。
元の点列を残すのは、表示（FR-5.3）で測定点をそのまま示せるようにし、補間の方法を後で変えても保存データに手を入れずに済むようにするためである。

### 5.2 任意方向の利得

水平面と垂直面の 2 断面から任意方向の利得を求める方法として、加算法を採る。

```
G(φ, θ) = G_peak − min( (G_peak − G_h(φ)) + (G_v(0) − G_v(θ)), A_max )
```

`G_peak` は方位断面の主ビーム方向の利得 `G_h(0)`、`A_max` は減衰の上限（既定 40 dB）である。
仰角断面は主ビーム方向との差だけを使うので、2 断面の主ビーム方向の値が食い違っていても、方位断面の上では元の値と一致する。

軸対称に近いパターンは次の式で求める。
α は軸からの角度、β は軸まわりの角度（局所 +z を 0 度とする）である。

```
G(α, β) = G_off(α) + sin α · (G_around(β) − G_around(0))
```

軸まわりの偏差に sin α をかけるのは、軸の上で利得が向きによらず一つに決まるようにするためである。
加算法は 3GPP のアンテナモデルでも使われる近似で、2 断面だけから計算でき、断面の上では元の値と一致する。
方式は関数一つに閉じ込め、後で重み付き補間などに差し替えられるようにする。

加算法が成り立つのは、2 断面がどちらも最大利得の方向（主ビーム方向）を含むときに限る。
主ビーム方向を含まない断面を使うと、主ビーム方向での利得が断面の値に引きずられる。
たとえば、下向きの天井設置 AP で「天井面に平行な断面」を水平断面として使うと、真下の利得が水平方向の利得と同じになってしまう。

このため、パターンを次の二種類に分けて扱う。

- **指向性パターン**：主ビーム方向を含む 2 断面（方位断面と仰角断面）を持つ。加算法で合成する。
- **軸対称に近いパターン**：天井設置 AP のデータシートに多い形で、主ビーム軸のまわりの断面（軸に垂直な面内の変化）と、軸を含む断面（軸からの角度ごとの利得）を持つ。軸からの角度で軸を含む断面を引き、軸まわりの角度で軸に垂直な断面の偏差を加える。

取り込み時に、どちらの形かを利用者が選ぶ。

### 5.3 AP の向き

AP は、設置方法（天井設置、壁設置）、方位角、チルトから回転行列を作る。
アンテナの局所座標は、+x を主ビーム方向とし、+z を AP の背面から見た上方向とする。
指向性パターンの方位断面は xy 平面、仰角断面は xz 平面にとる。
軸対称に近いパターンの軸は +x とする。

- **天井設置**：局所 +x をワールドの下向き（−Z）に向ける。方位角は局所 +z の水平方向の向きを決め、軸まわりの断面の向きに効く。チルトは主ビーム軸を鉛直から傾ける角度とする。
- **壁設置**：局所 +z をワールドの上向きにし、+x を方位角の方向に向ける。チルトは主ビーム方向の俯角とする。

受信点への方向ベクトルを局所座標に変換し、指向性パターンでは `φ = atan2(y, x)`、`θ = asin(z)` で、軸対称に近いパターンでは軸からの角度 `acos(x)` と軸まわりの角度 `atan2(z, y)` で表を引く。
実機のデータシートでの断面の向きが上の取り決めと異なる場合に備え、AP モデルに断面の回転補正（軸まわりの角度のずれ）を持たせる。

### 5.4 チャネル表

チャネル表は `packages/domain` に置き、チャネルごとに中心周波数と、チャネル幅ごとの占有周波数範囲を持つ。
同一チャネル干渉の判定（FR-8.6）は、この周波数範囲の重なりで行う。

計画を立てるための道具なので、選べるチャネルは国内の電波法の範囲に限らず、IEEE 802.11 で定義された範囲まで広げる。
これは FR-6.4（国内で使える範囲に限る）を利用者との合意で緩めたものである。
代わりに、各チャネルに国内で使えるかどうかの印を持たせ、国内で使えないチャネルを選ぶと UI で注意を出す。

| 帯域 | チャネル | 中心周波数 | チャネル幅 | 国内で使えるもの |
| --- | --- | --- | --- | --- |
| 2.4 GHz | 1〜14 | 2407 + 5n MHz（14ch は 2484 MHz） | 20、40 | 1〜13（14ch は 802.11b のみ） |
| 5 GHz | 36〜177（4 刻み、UNII-1〜4） | 5000 + 5n MHz | 20、40、80、160 | W52（36〜48）、W53（52〜64）、W56（100〜144） |
| 6 GHz | 1〜233（4 刻み） | 5950 + 5n MHz | 20、40、80、160、320 | 1〜93（5925〜6425 MHz） |

40 MHz 以上の幅では、規格で決まった組み合わせだけを選択肢に出す。
国内で使えるかどうかの印は、法令の改正に合わせて表だけを直せば済むようにする。
表の値は実装時に最新の告示と規格で確かめる。

## 6. 伝搬計算

### 6.1 計算式

受信点 r における AP のラジオ t の推定受信電力は次のとおりとする（FR-7.1、FR-7.2、FR-7.4、FR-7.6、FR-7.7）。

```
RSSI = P_tx + G_tx(φ, θ) + G_rx − PL(d, f) − Σ L_wall − Σ L_slab
PL(d, f) = FSPL(1 m, f) + 10 · n · log10(d / 1 m)
FSPL(1 m, f) = 20 · log10(f_MHz) − 27.55
```

- 計算はワールド座標（3 章）で行う。AP の位置は `(x, y, elevationM + heightM)`、受信点は受信するフロアの格子点を `(x, y, elevationM + 受信高さ)` に置いたものとする。どちらもフロアの床面の標高を足した絶対の高さである。
- `d` は AP と受信点の 3 次元距離とし、1 m 未満は 1 m として扱う。
- `G_tx` は、AP から受信点への向きをその AP のフロアのフロア座標に戻してから表を引く。AP の方位角はフロア座標で測るためである。実装では、アンテナの基底にフロアからワールドへの回転を掛けておく。
- `f` はラジオのチャネルの中心周波数とする。
- `n` は帯域ごとの減衰指数で、既定値 2.0 のとき自由空間損失と一致する。
- `Σ L_wall` は、AP と受信点を結ぶ 3 次元の線分が横切る壁区間の減衰量の合計である（6.1.1 節）。
- `Σ L_slab` は、同じ線分が横切る床スラブの減衰量の合計である（6.1.2 節）。

同じフロアの AP と受信点では、壁の高さ（FR-4.10）を指定しない限り、版 2 までの計算と同じ値になる。
AP の高さと受信高さがどちらも 0 m から階高までに入れば、線分はその間を通り、床スラブも横切らないためである。

#### 6.1.1 壁

線分を平面に投影し、壁区間と交差するかを平面で判定する。
交差したら、線分の上での交点の位置 `t`（AP を 0、受信点を 1 とする）から高さ `z(t) = z_AP + t · (z_受信点 − z_AP)` を求める。
`z(t)` が壁区間の高さの範囲に入るときだけ、その区間の減衰量を加える。
高さの範囲は、壁のフロアの床面の標高に `bottomM` と `topM` を足した絶対の高さで、下端を含み上端を含まない半開区間とする。
上下に積んだ壁（下のフロアの壁の上端と上のフロアの壁の下端が一致するもの）の境目を通る線分で、減衰を二重に数えないためである。

開口部のある区間は、高さの範囲ごとに別の壁区間として登録する（4.1 節）。
たとえば、高さ 0〜2.0 m のドアがある階高 3 m の壁では、同じ平面の線分を、ドアの材質で 0〜2.0 m、壁の材質で 2.0〜3.0 m の 2 区間にする。
平面の交差判定は同じ線分で 2 回行うことになるが、開口部の数は壁の区間の数に比べて少ないので、まとめる工夫はしない。

計算に含めるフロア（6.4 節）の壁区間を一つの集合にまとめ、どのフロアの壁かは区別しない。
位置合わせをしていないフロアを受信するときは、そのフロアの壁区間だけの集合を使う。
階高を超える壁が上のフロアの空間に入っていても、そのまま扱える。

#### 6.1.2 床スラブ

フロア k の床スラブは、高さ `elevationM_k` の水平な面とする。
線分が、下端を含まず上端を含む区間 `(min(z_AP, z_受信点), max(z_AP, z_受信点)]` で床面の高さを含むとき、床面を横切るものとする。
受信点や AP がちょうど床面の上にある場合（受信高さ 0 m）は、そのフロアの側にあるとみなすためである。
横切る点を平面に投影し、フロア k の図面座標に戻して、次の両方を満たすときに床スラブの材質の減衰量を加える。

- 図面の範囲（トリミング範囲、無ければ図面全体）に入る。
- どの吹き抜けの多角形にも入らない。

図面の範囲の外を床スラブなしとするのは、建物の外（図面の余白）を通る経路に床の減衰を加えないためである。
3D ビューで床を描く範囲（13 章）と同じになる。

床面の高さが同じフロアが複数あるときは、それらを一つの面として扱い、横切る点がどれかの範囲に入れば、入ったもののうち減衰量の最も大きい材質で一度だけ加える。
同じ高さで図面を分けたフロア（別棟や、同じ階を 2 枚の図面に分けたもの）で、重なった部分の床を二重に数えないためである。

#### 6.1.3 交差判定の境界

線分が折れ線の頂点をちょうど通ると、隣り合う 2 区間の両方と交差したと判定し、減衰を二重に数えてしまう。
これを避けるため、各区間の交差判定を始点側を含み終点側を含まない半開区間で行う。
この扱いで二重計上を防げるのは、同じ折れ線の頂点に限る。
別々の壁が端点を共有する角を線分がちょうど通る場合は、0 回か 2 回数えることがある。
格子点と AP がちょうど角の延長線上に並ぶ場合に限られるので、今回は対処しない。

### 6.2 計算の単位とキャッシュ

計算は「受信するフロアとラジオの組ごとの受信電力の格子」を単位とする。
格子は受信するフロアのフロア座標の軸に沿って置き、範囲は、トリミング範囲があればその矩形、なければ図面画像の全体とし、フロア座標に変換して決める。
格子点は計算のときにワールド座標に移す。
受信するフロアとラジオの組一つにつき、この範囲の格子（30 m × 30 m、0.5 m なら 61 × 61 点）を `Float32Array` に計算し、キャッシュする。
ラジオは、受信するフロアと同じフロアのものに加え、対象範囲（FR-7.8、6.4 節）のフロアのものを含む。
縮尺の小さい図面では範囲が広くなり点数が増えるので、トリミングで計算範囲を絞れることを UI で示す。

ヒートマップ（FR-8.1〜8.6）は、キャッシュした格子を組み合わせて作る。

- **最大受信電力（FR-8.2、FR-8.3）**：対象ラジオの格子の要素ごとの最大値。
- **AP 数（FR-8.5）**：閾値以上のラジオの数。
- **同一チャネル干渉（FR-8.6）**：閾値以上で届くラジオのうち、占有周波数範囲が重なる組があるかどうか。
- **カーソル位置の一覧（FR-8.7）**：各ラジオの格子を双線形補間して引く。再計算は要らない。他のフロアの AP にはフロア名を添える。

AP の絞り込み（FR-8.3）の選択肢には、計算に含めた他のフロアの AP も、フロアごとにまとめて出す。

キャッシュのキーは、ラジオの計算に効く値（位置、高さ、向き、パターン、出力、チャネル、AP のフロアの位置合わせと標高）と、その組の計算に効く環境から作る。
環境は、フロアごとの「壁、吹き抜け、床スラブの材質、図面の変換、位置合わせ、標高、階高」の要約と、材質、設定から作る。
組の計算に効くフロアは、AP と受信点の高さの範囲（受信するフロアのすべての格子点と AP の高さの最小から最大まで）に、壁の高さの範囲か床面が重なるフロアとする。
上下に離れたフロアの壁を変えても、その間を通らない組は計算し直さずに済む。

- AP を 1 台動かしたときは、その AP のラジオを含む組だけを計算し直す。
- フロアの壁や吹き抜けを変えたときは、そのフロアが効く組だけを計算し直す。
- 材質か設定が変わったときは、すべての組を計算し直す。

### 6.3 性能（NFR-1）

NFR-1 の条件では、ラジオ 10 本（1 帯域）× 3,721 点 × 壁区間 300〜600 本で、交差判定がおよそ 1,100 万〜2,200 万回になる。
M1 のベンチマーク（`packages/propagation` の `pnpm bench`）では、単純な線分交差判定と外接矩形による絞り込みだけで、この条件の 1 帯域の計算が単一スレッドで約 40 ms だった。
格子が細かくなったり壁が増えたりして足りなくなったら、壁区間を一様格子に登録し、線分が通る格子だけを調べる方式を加える。

フロアをまたぐ計算では、受信するフロアごとのラジオの数がフロアの数だけ増え、調べる壁区間も全フロア分になる。
NFR-1 の条件のフロアを 3 つ重ねると、受信するフロア一つあたりラジオ 30 本 × 3,721 点 × 壁区間 900〜1,800 本で、外接矩形の絞り込みだけでは交差判定が 1 億〜2 億回になる。
外接矩形は平面で見るので、上下に重なった別のフロアの壁区間は絞り込めない。
このため、次の絞り込みを加えた。

- **高さによる絞り込み**：壁区間をフロアごとの集合にまとめ、集合の高さの範囲（絶対の高さ）が線分の高さの範囲と重ならなければ、集合ごと調べない。集合の中でも、区間ごとの高さの範囲で平面の判定の前に除く。同じフロアの組では、他のフロアの壁区間を一つずつ見ずに済む。

ベンチマーク（`pnpm bench`）では、1 フロア（壁区間 466 本、ラジオ 10 本）が約 47 ms、この条件のフロアを 3 つ重ねて真ん中のフロアで全フロアのラジオ 30 本を受ける場合（壁区間 1,445 本）が約 290 ms だった。
編集中のフロアの更新を 1 秒程度に収める条件（NFR-1）を満たすので、一様格子は入れていない。
足りなくなったら、次の方式を加える。

- **一様格子**：壁区間を平面の一様格子（一辺は壁区間の平均の長さ程度）に登録し、線分を平面に投影して通るセルだけを順にたどる（Amanatides–Woo 法）。一つの線分で同じ壁区間を二度調べないよう、区間ごとに最後に調べた線分の番号を持つ。

計算はブラウザの Web Worker で行う。
M1 のベンチマークでは 1 帯域の計算が単一スレッドで約 40 ms だったので、Worker は一つとし、ラジオごとの結果のキャッシュをその中に持つ。
アンテナパターンは関数にコンパイルして使うので、Worker 間では受け渡せない。
そのため、メインスレッドは文書を送り、計算の入力は Worker の中で組み立てる。
送る文書は全フロアとし、写真のピンなど計算に効かないものだけを除く。
対象範囲の外のフロアの壁や、計算に含めないフロアの床スラブも使うためである（6.4 節）。
壁区間と床スラブの集合は受信するフロアによらず共通なので、Worker の中で一度作り、環境が変わるまで使い回す。
フロアをまたぐ計算で一つの Worker では足りなくなったら、受信するフロアごとに Worker を分け、この集合はそれぞれの Worker が持つ。
メインスレッドは計算を待たないので、計算中も UI を操作できる。
編集が連続したときは、最後に頼んだ計算の結果だけを使う。
再計算は文書の変更から 150 ms のデバウンスをかけて始める（FR-8.8）。
最大値、AP 数、同一チャネル干渉の合成と、カーソル位置の値の読み出しは軽いので、メインスレッドで行う。

伝搬計算を各クライアントで行うのは、サーバの負荷が編集者数に比例して増えるのを避けるためである。
全員が同じ文書から同じ関数で計算するので、結果はクライアント間で一致する。

### 6.4 計算しない条件

スケールが未校正のフロア（FR-2.5）では計算せず、ヒートマップの代わりに校正を促す表示を出す。
無効化したラジオは計算の対象から外す（FR-7.5）。

フロアをまたぐ計算に含めるフロアは、次のすべてを満たすものとする（FR-7.5、FR-7.8）。

- スケールを校正済みである。
- 基準フロアであるか、位置合わせ（FR-3.2）をしている。
- 受信するフロアからの距離が `crossFloorRange` 以内である。距離は、全フロアを `order` の順に並べたときの位置の差とする。

`crossFloorRange` が絞るのは AP だけで、壁と床スラブは範囲の外のフロアのものも含める。
範囲の外のフロアの壁でも、階高を超える壁なら経路をさえぎることがあるためである。

位置合わせをしていないフロアは、そのフロアだけで計算する。
そのフロアの AP は他のフロアの計算に含めず、そのフロアの計算には他のフロアの AP、壁、床スラブを含めない。
3D ビューでは位置合わせをしていないフロアを基準フロアと同じ原点に置くが、計算でそうしないのは、位置が誤っていると誤った結果を正しいもののように見せてしまうためである。

計算に含めない（未校正か位置合わせをしていない）フロアの床面の高さを線分が横切るときは、そのフロアの床スラブは全面にあるものとして減衰を加え、壁は無いものとする。
図面の範囲と吹き抜けをワールド座標に置けず、床がないとすると上下のフロアの間で電波が強く出すぎるためである。
材質は 6.1.2 節と同じく、`slabMaterialId` か床スラブのプリセットを使う。
これらの扱いをしたときは、ヒートマップの凡例のそばに、どのフロアをどう扱ったかを示す。

## 7. 実測サーベイへの備え

実測サーベイのデータは、地点数が多く共同編集の対象にもならないので、Yjs 文書ではなくデータベースの `survey_datasets` と `survey_points`（フロア ID、図面座標、BSSID、帯域、チャネル、RSSI、測定日時）に置く予定とする。
推定値との比較は、`propagation` の任意地点を評価する関数を使う。
今回はテーブルを作らず、図面座標で位置を保存する方針（3 章）と、任意地点の評価関数だけを用意しておく。

## 8. 図面の取り込み

1. 利用者が PDF、PNG、JPEG をアップロードする。サーバは元ファイルを blob として保存する。
2. PDF の場合、サーバはページ数とページごとの縮小画像を返す。利用者はページと解像度（既定 200 dpi、上限 300 dpi）を選ぶ。
3. サーバは worker thread でページをラスタ化し、PNG として保存する。画像の場合はそのまま使い、長辺が上限を超えるときだけ縮小する。
4. クライアントはフロアの `plan` に、元ファイルと画像の SHA-256、`unitsPerPx` を書く。

回転とトリミング（FR-2.3）は `plan.rotationDeg` と `plan.crop` に書くだけで、画像は作り直さない。
画像の長辺は、WebGL のテクスチャ上限を考えて 8,192 ピクセルまでとする。

## 9. 壁の自動抽出

### 9.1 処理の流れ

壁抽出（FR-4.1、FR-4.2）はサーバの worker thread で、次の順に行う。

1. 図面画像をグレースケールにし、閾値（固定値か大津の方法）で二値化する。
2. 開閉処理で、壁より細い線（寸法線、文字、ハッチング）を消す。消す太さは「最小の壁の厚さ」で指定する。
3. 残った領域を細線化して中心線を得る。細線化は opencv.js の標準ビルドに含まれないので、Zhang-Suen 法を TypeScript で書く。
4. 中心線の画素を、分岐点と端点（隣の画素の数が 2 でない点）で区切ってたどり、枝ごとの画素の列にする。縦か横の隣でつながる斜めの隣は数えず、角や交点に偽の分岐点ができないようにする。
5. 枝を Douglas-Peucker 法で間引いて折れ線にする。
6. 最小の長さより短い折れ線を捨てて返す。クライアントが図面座標に変換する。

確率的 Hough 変換（HoughLinesP）で線分を得て、同一直線上の断片をつなぐ方式も残し、画面で切り替えられるようにする。
合成図面では、中心線をたどる方式の再現率が 100%、Hough 変換の方式が 92% だったので、前者を既定にする。
Hough 変換の角度の刻みは 0.25° とする。1° では、長い線で量子化した向きが数ピクセルずれ、線分が途切れたり画素から外れたりした。
つないだ線分は、細線化した画素を 1 画素ずつたどって確かめ、画素のない区間が結合距離より長ければそこで切る。
画素で覆われた割合が 8 割に満たない区間（点在する画素を結んだだけの線）は捨て、残った区間は画素に最小二乗で直線を当てはめて引き直す。
これで、図面に線のないところへ線分が伸びるのを防ぐ。

壁を塗りつぶさず 2 本の細い線で描いた図面のために、手順 2 の代わりに輪郭を抽出する前処理も選べるようにする。
二値画像の輪郭を 1 画素幅で描き、最小の長さの 2 倍より短い輪郭（文字、記号）を捨ててから、手順 3 以降と同じく細線化して検出する。
この前処理では、壁の中心線ではなく両側の線が候補になる。

Hough 変換の方式では、近くに並ぶほぼ平行な線分を、その間の 1 本にまとめる処理も選べる。
向きの差が 3° 以内で、間隔が指定の値以下、線に沿った方向に短いほうの半分以上が重なる組を、2 本の真ん中の線にし、両方の範囲を覆うよう伸ばす。
間の線には画素がないので、画素による確かめの後に行い、その後もう一度同一直線上の断片をつなぐ。
二重線の合成図面に輪郭の前処理と合わせて使うと、壁の中心線の再現率は 92% だった。

調整できる値は、前処理、二値化の閾値、最小の壁の厚さ、Hough の投票数、最小線分長、結合距離、平行な線分をまとめるかどうかとその間隔とする。

### 9.2 候補の扱い

抽出の要求は非同期のジョブとし、`POST` でジョブを作り、クライアントが結果を取りに行く。
時間の上限は 60 秒とする（NFR-2）。

抽出した候補は、要求したユーザーのローカル状態に置き、Yjs 文書には書かない。
他の編集者に未確定の候補を配信する必要がないためである。
採用した候補（FR-4.3）だけを、既定の材質を持つ壁として一つのトランザクションで文書に書く。

### 9.3 リスク

図面の描き方（壁を塗りつぶすか、二重線で描くか、線の太さ）によって、抽出の精度が大きく変わる。
実際の図面は後日提供されるので、M1 では処理時間の見込み（NFR-2）だけを、合成した図面で確かめる。
抽出の精度の評価と、二重線の壁を 1 本の中心線にまとめる処理が要るかの判断は、図面が届いてから M8 で行う。

M1 の技術検証（`packages/wall-extraction` の `pnpm spike`）の結果は次のとおりである。

- A3 横を 200 dpi（3308 × 2339 px）でラスタ化するのに約 0.7 秒、抽出に約 0.4 秒かかり、worker thread の起動を含めても約 2 秒で終わった。NFR-2 の 60 秒には十分な余裕がある。
- 合成図面の壁 24 本のうち 83% を検出した。細線化の段階で、寸法線、文字、ハッチング、ドアの軌跡は消え、壁の中心線だけが残った。
- 見逃しの原因は、HoughLinesP が 1 本の壁を細かい断片に分けて返すことだった。M8 では、細線化した画素を直接たどって折れ線にし、Douglas-Peucker 法で頂点を間引く方式を試し、Hough 変換と比べる。
- opencv.js 5 の HoughLinesP は、線分を N × 1 ではなく 1 × N の行列で返すことがある。読み出しは要素数で数える。

## 10. 共同編集

### 10.1 同期

クライアントは HocuspocusProvider でサーバに接続し、プロジェクト ID を文書名にする。
サーバは Hono のルート（`/collab`）で `@hono/node-server` の `upgradeWebSocket` を使って WebSocket を受け、`onOpen` で Hocuspocus の `handleConnection` に生の WebSocket と Request を渡す。
Hocuspocus の組み込み `Server` クラスを使わないので、`onMessage` と `onClose` で受けたイベントを、返された接続オブジェクトの `handleMessage` と `handleClose` に自分で渡す。
Hocuspocus は Database 拡張で `yjs_documents` を読み書きする。
保存はデバウンスをかけて行う。

### 10.2 権限の確認

WebSocket の接続時に、Hocuspocus の `onConnect` でセッション Cookie（`requestHeaders` に含まれる）を検証し、文書名からプロジェクトの権限を引く。
`onAuthenticate` はクライアントがトークンを送ったときの認証処理であり、トークンを送らないクライアントに対して必ず呼ばれるとは確認できていない。
そのため、すべての接続で呼ばれる `onConnect` を確認の場所とする。
Hocuspocus v4 は、クライアントが文書ごとに送る認証メッセージを受けるたびに、トークンの有無によらず `onConnect` と `onAuthenticate` を呼ぶ（ソースで確認した）。
トークンなしの接続と閲覧者からの書き込みが拒否されることは、サーバの結合テストで確かめている。

- 権限がなければ例外を投げて接続を拒否する。
- 閲覧権限だけなら `connectionConfig.readOnly = true` にし、サーバがその接続からの更新を受け付けないようにする。
- 権限の変更、ユーザーの無効化、プロジェクトの削除が起きたら、該当する接続の WebSocket をサーバから閉じる。クライアントは自動で再接続し、その時点の権限で認証し直す。権限がなければ再接続は拒否される。
  文書単位の接続を閉じるだけでは、クライアントが認証し直さないので、閲覧から編集への変更が反映されない。

UI で編集操作を隠すだけでは、閲覧者が改変したクライアントから文書を書き換えられる。
そのため、書き込みの拒否はサーバで行う。

### 10.3 awareness

awareness には、ユーザー名、表示色、表示中のフロア、カーソルの図面座標、選択中の要素 ID、ドラッグ中の要素の仮の位置を載せる（FR-10.3）。

ドラッグ中の位置を文書に書かないのは、ドラッグの途中経過が undo の履歴と保存データに残るのを避けるためである。
ドラッグ中は awareness で他のユーザーに仮の位置を見せ、手を離した時点で一度だけ文書に書く。

### 10.4 オフラインと undo

y-indexeddb で文書をブラウザに保存し、切断中も編集を続けられるようにする（FR-10.4）。
再接続すると、Yjs の差分同期で変更が統合される。

undo と redo（FR-10.5）は `Y.UndoManager` で行い、`trackedOrigins` を自分のクライアントからの変更に限る。
こうすると、他のユーザーの変更を巻き戻さずに、自分の操作だけを戻せる。

undo の単位は、画面の 1 回の操作（1 回の書き込み）とする。
`Y.UndoManager` は既定で短い間隔の変更を一つにまとめるが、それでは素早く続けた別々の操作（結合とドアの追加など）が一度に戻ってしまう。
そのため、書き込みのたびに undo の区切りを入れ、数値の入力のように続けて変わる値だけを短い間隔でまとめる。

## 11. 認証とユーザー管理

- ログインはユーザー名とパスワードで行い、成功したら HttpOnly、SameSite=Lax のセッション Cookie を発行する（FR-1.1）。
- 最初の管理者は、初回起動時に環境変数 `ADMIN_USERNAME` と `ADMIN_PASSWORD` から作る。
- 管理者はユーザーを作成、無効化できる（FR-1.2）。無効化するとセッションを消し、WebSocket の接続を切る。
- CSRF 対策として、SameSite=Lax に加え、状態を変える API には独自ヘッダを必須にする。
- ファイルの取得 API は、`project_files` でプロジェクトとの対応を引き、権限を確かめてから返す。

## 12. 現場写真

写真はサーバが受け取り、sharp で縮小画像を作り、EXIF の撮影日時を読む（FR-9.4）。
EXIF の位置情報は使わないうえ、保存しておく理由もないので、保存前に取り除く。
写真ピンは次の形で文書に持つ（FR-9.1、FR-9.2）。

```ts
type PhotoPin = {
  position: Vec2;   // 図面座標
  photos: { sha256: string; thumbSha256: string; directionDeg?: number;
            memo: string; takenAt?: string }[];
};
```

## 13. 可視化

ヒートマップは格子の値を色の対応表で RGBA に変換し、テクスチャにする。
2D ビューでは Konva の画像として図面の上に重ね、3D ビューでは各フロアの床面に貼る。
閾値未満を塗らない表示（FR-8.4）は、対応表の該当区間を透明にして実現する。

他のフロアの重ね表示（FR-3.3）は、ワールド座標を経由して編集中のフロアの図面座標に変換し、フロアごとの透過率で描く。

疑似 3D ビュー（FR-3.4〜3.6）は、フロアを `elevationM` の高さに置き、図面とヒートマップを床面に、壁を壁ごとの高さの範囲（4.1 節）を持つ面として描く。
開口部の区間は、開口部の高さの範囲を開口部の材質の色で、それ以外を壁の材質の色で塗る。
高さの倍率（FR-3.7）は表示だけの設定で、床の標高、階高、AP の高さに同じ倍率をかけて置く。AP の球やフロア名は引き伸ばさない。
吹き抜け（FR-3.8）は、図面とヒートマップの長方形から吹き抜けの多角形を抜いて三角形分割した面にする。長方形からはみ出した部分は切り取ってから分割する。重なった吹き抜けはまとめないので、重ねずに描く。
3D ビューは文書を読むだけで、書き込みの経路を持たない。

## 14. デプロイ

`compose.yaml` には `app` サービスだけを置く（NFR-5）。
`app` は、サーバのビルドと Web アプリの静的ファイルを含む一つのイメージで、API、WebSocket、静的ファイルを同じポートで提供する。

データは名前付きボリューム `data` に置き、SQLite のファイル（`data/app.db`）とアップロード領域（`data/uploads/`）をその下に並べる。
サーバは起動時にマイグレーションを適用する。
