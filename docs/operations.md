# 運用の手順

## 配備

`compose.yaml` の `app` サービスが、API、同期の WebSocket、Web アプリの静的ファイルを一つのポートで提供する（NFR-5）。
設定は環境変数で渡す。

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `ADMIN_USERNAME` | `admin` | 最初の管理者のユーザー名 |
| `ADMIN_PASSWORD` | （必須） | 最初の管理者のパスワード。ユーザーが一人もいないときだけ使う |
| `PORT` | `3000` | ホスト側で公開するポート |
| `COOKIE_SECURE` | `false` | HTTPS の背後で動かすときは `true` にし、Cookie に Secure を付ける |

HTTPS で公開するときは、前段にリバースプロキシを置き、`/collab` の WebSocket を中継する設定にする。

## データの置き場所

データは名前付きボリューム `data`（コンテナの `/data`）に置く。

| パス | 内容 |
| --- | --- |
| `/data/app.db` | SQLite のデータベース（ユーザー、プロジェクト、権限、AP モデル、Yjs 文書） |
| `/data/uploads/` | アップロードしたファイル（図面、写真）。SHA-256 をファイル名にして置く |

削除したプロジェクトは 7 日後に消え、どのプロジェクトからも参照されなくなったファイルもそのときに消える。
この処理は起動時と、その後 1 日ごとに行う。

## バックアップ

サーバを止めずにバックアップを取れる（NFR-6）。

```sh
./scripts/backup.sh            # backups/wifi-planner-YYYYmmdd-HHMMSS.tar.gz を作る
./scripts/backup.sh /mnt/nas   # 出力先を指定する
```

データベースは SQLite の `VACUUM INTO` で一貫した写しを作ってから固める。
書き込み中のデータベースのファイルをそのまま写すと、壊れた写しになることがあるためである。
定期的に取るときは、このスクリプトを cron などで動かす。

## 復元

復元すると今のデータは消えるので、必要なら先にバックアップを取っておく。

```sh
./scripts/restore.sh backups/wifi-planner-YYYYmmdd-HHMMSS.tar.gz
```

スクリプトは `app` を止め、データの領域をバックアップの内容に置き換えてから、`app` を起動し直す。

## 更新

```sh
git pull
docker compose up -d --build
```

データベースのマイグレーションは起動時に自動で適用する。
更新の前にバックアップを取っておくと、問題があったときに戻せる。

## プロジェクトの持ち出し

プロジェクトの一覧の「エクスポート」で、図面と写真を含むプロジェクト全体を ZIP に書き出せる（FR-1.5）。
「インポート」でその ZIP を読み込むと、新しいプロジェクトとして作られる。
別の環境への移行や、特定のプロジェクトだけの保管に使う。
